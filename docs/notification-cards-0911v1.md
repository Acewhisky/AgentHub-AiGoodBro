# 通知卡与完成事件 · 0911v2

相较 0911v1：任务完成卡已接到现有 Codex 实时快照，不再仅提供 DTO 组件。任务结束、额度窗口变化、重置卡新增及账号切换分别呈现。

| 事件 | 标题重点 | 颜色 |
| --- | --- | --- |
| Codex 任务完成 | 任务已完成，打开原任务查看结果 | 绿色 |
| 手动或自动切换成功 | 实际来源、脱敏源账号与目标账号 | 蓝色 |
| 切换失败 | 未完成及结构化原因 | 红色 |
| 官方额度窗口变化 | 只报告官方窗口变化 | 青色 |
| 重置卡新增 | 新增数量及可用数量 | 紫色 |
| 低额度 | 实际触发的阈值与窗口 | 橙色 |

UsageStore 的现有 onSnapshot 同时喂入完成观察器。必须在同一连接中先观察到稳定 thread/turn 的运行状态，再收到时间顺序正确、5分钟内的 completed 才通知。首次快照已经结束、归档、进程零退出、报告文件、失败、取消、断线前记录及重复回放都不构成该证据。确认缓存和活动集合各有上限。

飞书完成发送复用现有发送器、总开关、完成类别开关、凭据读取和配置版本核验。停用、停止应用或修改配置会使旧回调失效；消息只含固定类别、时间和可选脱敏字段，不含原任务标题、正文、路径、账号邮箱或凭据。卡片不声称产物已验收。

Telegram/企业微信通过独立开关接收相同来源的完成事件，按通道保留自己的观察基线。详见[消息通道](message-channels-0911v1.md)。

飞书纯自检覆盖卡片中英文文案、事件区别、配置开关与迟到回调；观察器测试覆盖实时状态序列。全部使用合成输入及拦截传输，没有发送真实飞书消息，也没有验证用户收到。
